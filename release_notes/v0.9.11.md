
#### BREAKING COMPATIBILITY

- Removing the `ShellAccess` toolset.
- Instead, `shell_command` is now a system-level tool which can be enabled using the following configuration property
  - **No change** to configuring tool settings and supported environmental variables
  ```yml
  session:
    allow_shell_commands: true
  ```

#### NEW

- Created a toolset called `TextLineEditing` and moved the following `TextEditing` tools over to this toolset, because not all models support line-based editing and keeping them all together was adding to the model's context confusion.
  - `str_insert_in_text_file`
  - `str_replace_lines_in_text_file`
- Incorporating platform-specific sandboxing to cordon off the execution of commands
  - Adding `cordon` section to the configuration YAML
    - `confirm` property defaults to `true` which tries to confirm cordon is available or not for your platform.
    - `mode` property can be set to
      - `commands` (default) to run shell commands within a cordon
      - `unsafe` to not use a cordon
    - `policy` sub-section can be used to define custom policy rules
      - `read_only_paths: [...]` (default is `[]`) array of paths to allow read-only access from within the cordon; executables in these paths are allowed to be run as well.
      - `read_write_paths: [...]` (default is `[]`) array of paths where read and write access is allowed from within the cordon.
    - `workspace` sub-section can be used to enable presets specific to your workspace, currently supports:
      - `using_brew: true` (default false) to ensure brew-installed commands are reachable from within the cordon
      - `using_ruby:` in two ways
        - `using_ruby: true` (default false) to use platform-supplied Ruby, including `brew`-installed Ruby if `using_brew` is `true.
        - `using_ruby:`
          - `ruby_path: PATH_STR` will ensure the Ruby at this location is allowed
      - `using_python:` in two ways
        - `using_python: true` (default false) to use platform-supplied Python, including `brew`-installed Python if `using_brew` is `true.
        - `using_python:`
          - `venv_path: PATH_STR` will ensure Python virtual environment is allowed.

#### EXPERIMENTAL

- Add `/session pop_and_transform prefix=PROMPTPREFIX response=NEWRESPONSE [replace=yes/no]`
  - Transforms the last response into a prompt (with `prefix` pre-pended) message by the user,
    followed by a `response` message by the LLM,  creating a synthetic conversation
    and appending it to parent session history.
  - Combined with `replace=yes` this turns the last response (from the LLM) into a prompt
    as if we're attaching it to a conversation, and the `response` parameter becomes
    the LLM's response to the prompt.
  - Consider the following queries:
    - `/session push`
    - `Create a compaction checkpoint with the preceding conversations for use as a handoff to a session later.`
    - `/session pop_and_transform prefix="Here's a handoff; please confirm when ready to proced: " response="Understood, ready." replace=yes`
  - This replaces the entire current session with the compaction checkpoint, but as if it was entered by the user and accepted by the LLM.
  - Without `replace=yes` this exits the current session and injects the synthetic conversation, and you can continue from there, which lets a macro act as if you did a bunch of work and provided some input.
  - **Why experimental?** I don't know if this will be a standalone sub-command or if this is the final state.
- Add block support in macro definitions, which allows nested blocks of queries that can be conditionally exited using the `?break...` commands.
  - A block is started by using the `<enter>` key on a query line, with queries within the block in subsequent lines.
  - Example:
    ```yaml
    macro_name:
      description: ...
      queries:
        - prompt
        - <enter>:
          - nested prompt
          - ?break if ...
          - prompt
        - prompt after block
    ```
  - **Why experimental?** Not sure if `<enter>` is the final shape, and if these block entry commands would support parameters, etc.

#### IMPROVEMENTS

- Support Shift-Enter for multi-line editing by enabling `CSI u` mode. (Alt-Enter also works.)
- Support `skip_confirm_with_cordon` tool setting for `shell_command`, default is `false`. If set to `true` and shell command execution is within a cordon, user confirmation is not required for restricted terms and allowed but not approved commands.
  - **Dangerous** without caution. Logs a warning if skipping required confirmation.
    ```yaml
    tool_settings:
      shell_command:
        skip_confirm_with_cordon: true
    ```
- Support `execute_through_shell` tool setting for `shell_command`, default is `false`. If set to `true` and commands can use shell syntax for piping and redirection.
    ```yaml
    tool_settings:
      shell_command:
        execute_through_shell: true
    ```
- Tweak system prompt when sub-agents are allowed
- Modified query / prompt stack to be able to show a "stack trace" on error or when a condition aborts.
- Improved the "reason" parameter description for tool calls to ask for a summary of intent.
- Modified `get_current_datetime` tool to return local date/time and ISO-8601 format UTC value.
- Console stylesheet via configuration supports ANSI256 colour names as well as RGB colour tuples.
  ```yaml
  console:
    style_sheet:
      info:
        fg: medium_violet_red
      query_prefix_by_user:
        fg: [255, 255, 0]
  ```
